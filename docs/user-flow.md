# User flow

This describes the app from the perspective of the people using it — what each step feels like and why it works the way it does. For the cryptographic mechanism behind each step, see [encryption.md](encryption.md). For *why* the 1:1 cycle is structured this way and what each question is actually for, see [methodology.md](methodology.md).

## Getting an account

- **The very first account on a fresh instance** is created from the server's own command line: `bin/console app:create-activation-link <email> --admin`. This is deliberate — it's the one bootstrap step that has to happen outside the app itself, since there's no admin yet to invite anyone.
- **Every account after that** depends on how the instance is configured (its registration mode, see [deployment.md](deployment.md#core-every-production-deployment)): an invite from any authenticated user (`invite`), an invite from an admin only (`admin_only`), or — if the instance opts into it (`domain`) — open self-registration restricted to a specific email domain, gated by double opt-in: submitting your email is the first opt-in, clicking the link that gets emailed to you is the second. By default, self-registration is off (`invite`), so most instances still work the invite-only way described above.

Either way, activation works the same: the link is single-use and expires after 24 hours. Opening it prompts for a password. A link that can't be used any more says why: one that was already used points to the login page, and an expired invite offers a **Request new invitation** button, which emails the person who invited you (or the company's admins, if they can't re-invite any more) at most once a day. Admins see such an invite marked "Renewal requested" on the Invites tab, with a one-click **Re-send invite**. An expired self-registration link points back to sign-up instead, while sign-up is still open.

**This password is not "an account password" in the usual sense — choosing it is the moment your encryption key is created.** The app says so directly on the activation screen, because it's the single most consequential thing a new user does: that password, run through the derivation described in [encryption.md](encryption.md), is what everything else depends on.

> **Forgetting your password is recoverable, but not free.** "Forgot password?" on the login screen emails a reset link — but since the server has never had anything that could decrypt your old 1:1s, resetting genuinely can't hand that access back either. Instead, completing the reset generates a **fresh** encryption keypair, so the account itself is usable again immediately, but every 1:1 sealed under the old keypair becomes unreadable until each counterpart re-shares it: the app detects this automatically, shows a counterpart a "re-share access" banner on their 1:1 list, and one click re-seals the affected 1:1s' keys to the new keypair — no plaintext ever crosses the server to make that happen. New 1:1s and anything a counterpart already re-shared are unaffected either way. (If you still remember your current password and just want to change it, do that from Account Settings instead — see below — since it re-wraps your *existing* key rather than generating a new one, so nothing needs re-sharing at all.)

## Logging in

Email and password, same as anywhere. Behind that simple form: the password gets run through the same derivation again (never sent as-is), and the resulting key is checked against the server's copy in constant time. The UI shows an explicit "unlocking your data" state during this, since the derivation step is deliberately slow (see *why* in encryption.md) and can take a perceptible moment.

Once logged in, the session lives in two places with two different lifetimes:
- A regular httpOnly session cookie (server-side, like any web app) keeps you *authenticated*. It ends when the browser closes, or after 12 hours without any request to the server. A meeting page you have in front of you checks for updates every few seconds, so it stays signed in; in a background tab it doesn't.
- The unwrapped encryption key lives only in that browser tab's memory/`sessionStorage` — it survives a page refresh, but closing the tab clears it. This is a deliberate trade-off explained on the login screen itself, not a hidden limitation: convenience (no re-typing on every refresh) without persisting key material anywhere durable. Opening the app in a *new* tab is still authenticated (the session cookie is shared across tabs), but that tab has no key of its own yet — `App.svelte` detects this (`authState.unlockStatus`, checked via `checkUnlocked()` in `auth.svelte.ts`) and shows `UnlockTab.svelte`, a lightweight password-only re-entry screen, instead of rendering pages that would otherwise silently fail to decrypt anything.

Ticking **Remember this browser for 30 days** on the login form trades some of that for convenience, on that browser only: the session lasts 30 days from the login (whether or not it's used, and across browser restarts), and the encryption key is kept in the browser's own storage, so new tabs and links from emails or the calendar open without a password. Anyone who can use that browser can then read your 1:1s, so it isn't for a shared computer. Logging out forgets the key. If the device is lost, change your password from another one: that signs the lost device out. See [encryption.md](encryption.md#remember-this-browser).

## Account settings

A few self-service account controls, reachable from a link in the header once logged in:

- **Change password.** Unlike the forgot-password flow above, this is for someone who still remembers their current password and just wants a new one — it re-wraps the *same* existing keypair rather than generating a fresh one, so nothing becomes unreadable and no counterpart ever needs to re-share anything. That includes your own unpublished drafts, whose key comes from the keypair, not the password. After a forgotten-password *reset*, a draft saved before the reset can't be opened any more. It shows up as an empty draft with a notice instead of breaking the page. Requires entering the current password first, the same way any sensitive account action does.
- **Meeting reminder emails** can be turned off per-account — the meeting reminder (the day before, or the Friday before a Monday meeting) and the follow-up after a meeting that wasn't closed, specifically. The emails announcing a *new* 1:1 and a *changed meeting date* are not covered by this toggle and always go out: they are how the other participant learns a cycle started, or that the meeting moved.
- **Export your data** downloads everything currently visible to you — your own answers (including an unpublished draft, if you have one — flagged `myDraftUnreadable` instead if it can no longer be opened, e.g. after a forgotten-password reset), any counterpart's published answers, the shared topics, comments, outcomes, goals, and which questions were marked as discussed, plus your private notes in a separate `privateNotes` list (as last saved, and flagged `unreadable` instead if they can no longer be opened) — as a single JSON file, decrypted entirely in the browser. Nothing new is computed on the server for this; it's the same data the app already lets you see, fetched in one batch and gathered into a file instead of being displayed.
- **Delete your account** is permanent and, unlike the two actions above, does affect other people — but narrowly: your own profile and encryption keypair are removed, and any of your own still-unpublished drafts are lost, but every 1:1 you're part of stays exactly as your counterparts already see it. Nothing is cascaded or torn down on their side.

## Your 1:1 list

Once logged in, this is the home screen: every counterpart you have 1:1s with, sorted by next meeting date (soonest first) — there's no separate "manager dashboard"; someone with several direct reports just sees a longer list, sorted the same way as everyone else's.

A toggle switches between two views:
- **By date** — a flat, chronological list across every counterpart.
- **By person** — grouped by counterpart, each group showing that pair's full archived history plus two small trend sparklines (mood, workload) built from your own past answers with them, so a shift over many meetings is visible at a glance instead of buried inside individual 1:1s. A line only gets a point from a 1:1 that asked the question: a pair on the Quick check-in, which has no workload question, adds nothing to its workload line. Both are computed entirely in the browser from 1:1s you can already see — nothing new happens on the server for this.

If any of your 1:1s were sealed under a counterpart's now-outdated encryption key (see "forgetting your password" above), a banner appears at the top with a one-click "re-share access" action. A 1:1 whose meeting date has passed but which isn't archived yet gets a neutral "not closed" badge here, regardless of which view you're in. One left open for longer than its period (say, over a vacation) also gets a line above the list with a "Close and schedule the next one" link: it opens the meeting's archive form, where the suggested next date is the nearest one on the pair's cadence that isn't in the past. A still-open 1:1 using a meeting type other than the regular check-in (e.g. "Career growth") shows that type next to its date, in both views.

## Starting a new 1:1

Either the manager or the employee can start one:
1. Pick the counterpart by typing their email (a live-filtered list of existing accounts) — people you've already had 1:1s with show up first, so you're not scrolling the full company list every time.
2. Say who leads this 1:1: you ("I lead this 1:1", so you answer as the manager and your counterpart as the employee) or your counterpart. The options name your counterpart, and if the two of you already have a 1:1, a line under one of them says which role you have in the most recent one. That line is information only. Nothing is preselected, and the 1:1 can't be created until you pick: a role carried over from another meeting can be the wrong way round for this one, and the next 1:1s of the pair keep the roles of the first. The role is chosen for one colleague: it can't be picked before the colleague is, and changing the colleague clears it. (The app doesn't enforce that the two participants pick complementary roles; it trusts them to coordinate this themselves, the same way it trusts them not to share their own password with each other.)
3. Set a meeting date.
4. The first time a given pair meets, they also set how often they'll repeat this (weekly / every two weeks / monthly). Every 1:1 after the first for that same pair inherits the periodicity automatically — the form explains this rather than just silently hiding the field.

The form also asks for a meeting type, which decides the questions each side gets. **Regular check-in** is preselected. **Quick check-in** is its short form: mood and one free-text question for the employee, one question for the manager, with the agenda left to the shared topics list. The 1:1 after a Quick check-in is a Quick check-in too, unless someone picks another **Next meeting type** when archiving. The other built-in types (first 1:1, career growth, support & workload) are for one meeting, and the 1:1 after one of them is a Regular check-in, also for a pair that was on Quick check-ins before it: pick Quick check-in again when archiving.

Right after creating a 1:1, its page offers "Create another 1:1 with the same settings": the form reopens with the meeting type and periodicity kept, and the counterpart, role and date empty — for a manager setting up 1:1s with a whole team.

Creating the 1:1 is also the moment its encryption key is generated and handed to both participants (sealed to each one's public key, as described in encryption.md) — from this point on, both sides can decrypt everything in it, and no one else can.

## Filling it out

Each side answers their own set of questions privately — an employee side (mood, workload, feelings, growth, friction, achievements, things to discuss) and a manager side (how the period went, feedback, support, the employee's achievements worth recognizing, things to discuss). See [methodology.md](methodology.md#what-each-question-is-asking-and-why) for what each one is actually asking. No question is required, and the draft says so: a couple of topics to talk about is enough, and a side can be published with fields left empty. Answers autosave as a draft every second of inactivity, encrypted even before publishing with a key only you have (see [encryption.md](encryption.md#draft-key)).

**Private notes.** A panel on each 1:1 holds notes only you can read: your counterpart can't, and neither can the server or your company's admins ([encryption.md](encryption.md#private-notes)). Use it for anything you want to remember about the meeting that isn't for sharing. The notes autosave as you type, stay editable after the 1:1 is archived, and never become part of your published answers. On a wide screen they're a column beside the form that stays in view while you scroll, and on a narrow one a card under the meeting header. **Hide notes** takes the text off the screen, for screen sharing. If two tabs change the same notes, you're asked which version to keep, with keeping both as the default. A forgotten-password reset makes existing notes unreadable, so export your data first if you need to keep a copy.

**Finding a note.** **Report → My private notes** lists every note you've written, newest 1:1 first, with a filter by counterpart and a search over the notes' text, the counterpart's name and the date. It's read-only: a note is still written on its 1:1's page, which each entry links to. Because the page could put every note on the screen at once, a note's text appears only after you click **Show note** (or **Show all notes**), never by opening the page or by searching. Notes that can no longer be opened are listed too, marked as such. Like everything else about the notes, the list is put together in the browser: the server sees neither the notes nor what you search for. See [the decision record](decisions/2026-10-09-private-notes-in-reports.md).

**Publishing itself is one-way** — once you publish your side, there's no draft-recall back to a private, unpublished state, and it becomes visible to your counterpart. But you can still edit your own answers afterward, right up until the 1:1 is archived: click "Edit" on your side (at the top or bottom of it), change what you need, and save. While you edit, a bar with Save and Cancel stays at the top of the screen and shows when there are unsaved changes; Ctrl+S (⌘S on a Mac) saves too, and closing or reloading the tab with unsaved changes asks first (moving to another page inside the app doesn't, so save before you do). Unlike a draft, an edit isn't saved as you type. There's no time limit, and it's silent — your counterpart isn't notified and sees no "edited" marker, so treat this as a way to fix a mistake, not as a private undo button once someone's already read and responded to what you wrote. See [`docs/decisions/2026-09-07-editable-published-anketa-answers.md`](decisions/2026-09-07-editable-published-anketa-answers.md) for why it works this way.

Each side can only see the other's answers once *that* side has published theirs too — until then, it just shows "not published yet."

**If the connection drops.** A line at the top of the screen says so, on every page, and is replaced by "Back online" for a few seconds once the server answers again. On a 1:1's page your unpublished answers and your private notes are kept in the browser tab meanwhile (encrypted, like everything else), and are sent by themselves when the connection is back: keep the tab open, since that copy doesn't outlive it. Everything else — a comment, a topic, publishing, closing the 1:1 — fails with its usual error while offline and works again afterwards; nothing is queued. See [the decision record](decisions/2026-10-09-connection-loss-banner.md).

**Topics to discuss.** The first card on a 1:1 is a shared list of topics. Either side can add one at any time, before or after publishing, and the other side sees it within a few seconds: unlike your answers, a topic is shared the moment you add it, so jot things down here during the week and the other person arrives knowing what you want to talk about. Only whoever added a topic can edit or delete it; either side can tick it off as discussed during the meeting. When the 1:1 is archived the list is frozen, and the topics not ticked off move to the pair's next 1:1. 1:1s created before this list existed still have their "What else to discuss" question; newer ones don't, since the list replaces it (a company template that includes that question keeps it, and an admin can still add it to one).

**Marking questions as discussed.** During the meeting, either side can tick the circle beside any published question block, on either side, to mark it as discussed. The block dims so the rest of the agenda stands out, and the counterpart's open tab shows the same within a few seconds. It's only a meeting aid: unticked questions don't block archiving, and nothing reports on them. Once the 1:1 is archived the ticks stay as they were, read-only.

## Comments, outcomes, and goals

These three live alongside the questions and work throughout the 1:1's lifetime, not just before publishing:

- **Comments** can be left on individual answers, outcome items, goals, or goal checkpoints — a small collapsible thread under each one, both sides can post.
- **Outcomes** are a shared checklist ("meeting outcomes") either side can add items to — but only the person who added an item can check it off or edit it; the other side can only comment on it. This ownership rule is stated directly in the UI, not left implicit. See [methodology.md](methodology.md#outcomes-vs-goals--tactical-vs-strategic) for why outcomes and goals are two different, deliberately separate lists.
- **Goals** are the one part of a 1:1's content with real plaintext-server involvement (see encryption.md's ["deliberate plaintext exceptions"](encryption.md#deliberate-plaintext-exceptions); the other exception is a company's template library, which is configuration, not content) — a goal has a title, description, target date, and status (in progress / achieved / cancelled), editable only by whoever created it, plus a series of encrypted progress checkpoints anyone can add. A small info toggle on the goals section explains exactly which fields are and aren't encrypted, right where a user would want to know.

## Wrapping up a cycle

When the meeting date passes:
- From the day after, either side sees a "The 1:1 on … isn't closed yet" block with three options: **Close and schedule the next one** (jumps to the archive form described below), **Reschedule** (push the date, same 1:1 — also the answer to "we were on vacation"), or **Didn't happen** (archives this cycle as missed; the next 1:1 is still auto-created the same way as below, unless "don't create the next meeting" is checked). The wording is deliberately neutral: nothing is "overdue".
- Otherwise, either participant can **archive** it once both sides feel it's done, with the archive form's **Close and schedule the next one** button. Closing always asks first, since it can't be undone and neither side can publish or change answers afterwards: it says if one of you hasn't published, and if you have unpublished answers of your own it publishes them before closing, so they aren't left behind in a draft. "Didn't happen" asks the same way. Archiving does two things: it closes this cycle, and — unless "don't create the next meeting" is checked — it immediately creates the *next* 1:1 for the same pair, on the same periodicity, with a fresh encryption key generated and sealed the same way as the very first one. The form's **Next meeting type** sets the new 1:1's meeting type. It starts on the type that follows this 1:1 by default: a Quick check-in after a Quick check-in, a company template after itself, and a regular check-in after everything else, since the other built-in types don't repeat. It can be changed to any type; a one-meeting type's own next meeting is back to a regular check-in unless someone picks again. "Didn't happen" uses the same choice. Any unchecked items from the outcomes list, and any topics not ticked off as discussed, carry forward into the new 1:1 automatically, still encrypted, still requiring both participants' keys to read. Open goals carry forward too (their plaintext row is copied so status/history persists across cycles).
- **Swap roles in the next 1:1**, a checkbox under the archive form's **More options**, creates the next 1:1 with the manager and the employee the other way round; the line under it says who answers as which. It is the way to fix a pair whose roles were set wrong, since every next 1:1 otherwise inherits them. To fix it right away, tick the checkbox and close the 1:1, with **Close and schedule the next one** or, once its date has passed, **Didn't happen**: the next 1:1 is created at once with the right roles, and goals, unchecked outcomes and undiscussed topics carry forward as usual. The confirmation repeats who will answer as which before anything is closed. The 1:1 being closed keeps its roles, with whatever was answered in it (closing publishes your own unpublished answers first, as always). Either participant can tick it without asking the other, who finds the other role's questions in the next 1:1; the same checkbox swaps back at the next archive. Reports and the list's trend lines still group 1:1s by role, so a pair's history there splits at the swap.
- If either participant has been blocked by an admin in the meantime, auto-recreation simply doesn't happen — no error, it just stops.
- A pair can have a second open 1:1 alongside its regular one, e.g. a hand-created ad-hoc one using a different meeting template. Such a 1:1 is a *one-off*. It starts without the carried-forward goals, outcomes and topics, since the already-open one has them. Goals, outcomes and topics added inside it don't carry on to the pair's regular meetings either. Archiving it never auto-creates a next 1:1, so the pair's chain never forks into two. The create form says so before the 1:1 is created, with a link to the pair's open 1:1 for someone who was only looking for that one, and the archive form says so instead of offering the next-meeting controls. See [the decision record](decisions/2026-09-23-one-open-anketa-chain-per-pair.md).

The day before a scheduled meeting, both participants get one reminder email each; for a side that hasn't published their answers yet, it carries an extra line saying so. A Monday meeting is reminded on the Friday before instead, and the email says "on Monday" rather than "tomorrow", so a Monday meeting scheduled by then isn't reminded on Sunday. A Monday meeting scheduled after Friday's reminders went out still gets its reminder on Sunday. Moving a meeting to another day emails the counterpart the new date right away, and the meeting gets a reminder for its new date too, unless that reminder day has already passed. See [the decision record](decisions/2026-09-29-business-day-reminders.md).

If a meeting's day passes and nobody closes it, both participants get one follow-up email on the next business day (Monday, for a Friday or weekend meeting): "Did your 1:1 happen?", with a link to close it and schedule the next one, and a link to move it to another date. It is sent once; a meeting moved after it gets another one only after its new date. See [the decision record](decisions/2026-10-03-follow-up-email-after-unclosed-meeting.md).

**Calendar link** on a 1:1's page copies a permanent link to your 1:1s with that person, meant for the description of your recurring calendar event. It always opens the pair's current open 1:1, so it keeps working cycle after cycle; with none open, it offers to schedule the next one. The same link works for both of you. See [the decision record](decisions/2026-10-03-pair-calendar-link.md).

## Reports

Either side can generate a report across a date range — every achievement and growth-log entry from that period, and every goal touched in it with its full checkpoint history, decrypted and assembled entirely in the browser from 1:1s already accessible to you. The server never sees this aggregation; it just serves the same encrypted 1:1s it always would, fetched in one batch rather than one request per 1:1.

## Admin

Admins get one extra screen: the full user list, with the ability to invite, block/unblock (a reversible login gate — doesn't touch or expose any of that user's encrypted data), and grant/revoke admin status. None of this requires or grants access to 1:1 content — it's an authorization capability, entirely separate from the encryption model (see encryption.md's threat-model section for why that separation matters).

**Meeting templates.** Under **Admin → Templates**, an admin builds the company's own 1:1 templates. A new template starts as a copy of the Regular check-in. Each side's questions can be reordered or removed, standard questions (Mood, Workload, Achievements, …) added back, and custom questions added: a question with free text, a list of entries, a single choice or multiple choices. **Preview** shows both sides as participants will see them, and the editor won't save a template with a problem. Every save keeps the earlier version, so 1:1s created from it don't change. Archiving a template hides it from the pickers; restoring it brings it back. Template names, descriptions and questions are not end-to-end encrypted: everyone in the company can see them, and so can the server ([encryption.md](encryption.md#company-templates)). The editor says so, and asks you not to put people's names or reasons for a meeting in a template. Custom questions don't appear in the Report; standard questions keep working there.

**Sharing a template.** On a template's page, **Download file** saves it as a `.json` file, and **Copy share link** copies a link that shows its questions to anyone who opens it, without logging in. Both carry what's on the page, unsaved changes included. An admin who opens the link can **Install to company library**; anyone else in a company is asked to pass the link to an admin. **Import template** on the template list reads a downloaded file. Either way the template opens as a new, unsaved template to review and save; nothing is added until then. A name another of the company's templates already has, archived ones included, gets "(Imported)" added. The template is inside the link's `#` part, which the browser never sends to the server, and a template holds only its questions, never answers or notes. Check its text for internal names before sharing it. See [the decision record](decisions/2026-10-02-template-portability.md).

**Using a company template.** Anyone in the company can pick an active company template for a pair's meetings: when creating a 1:1 (the templates are listed under the built-in ones, and if there are none yet an admin gets a link to create one), or as the **Next meeting type** when archiving. The 1:1 gets the template's latest version, shows its name next to the meeting date and in the 1:1 list, and keeps that version for good: editing the template later changes only 1:1s created after the edit. A template recurs: the next meeting uses its latest version by default, at the pair's usual frequency. Once an admin archives it, the next meeting defaults to a Regular check-in, and the archive form says why. If a 1:1's questions can't be loaded, the page says so with a **Try again** button, and the 1:1 can still be archived. The data export includes each 1:1's meeting type and, for a company template, its name and questions.

## Language

The interface (English, Russian, Latvian, Spanish, German, French) is a pure client-side preference, switchable anytime, independent of what language a given account's notification emails go out in — those follow whatever the account holder last set explicitly, since the two can reasonably differ (e.g. someone reading the UI in one language while a colleague, or their own inbox habits, expect emails in another).
