# Decisions

Short, individually-linkable records of non-trivial decisions made *after* the
[`CLAUDE.md`](../../CLAUDE.md)/[`docs/history.md`](../history.md) split
(2026-08-22). Each is a single short file, not a paragraph appended to a
growing log — the point is that a later session can read the 5–10 lines
relevant to one decision instead of scanning a single ever-growing file.

Use this for something more substantial than a one-line change but not
foundational/hard-to-reverse enough for [`docs/adr/`](../adr/) (which is
reserved for the ~8 genuinely foundational architecture decisions). A rough
guide: if it changed behavior, closed a real gap, or reversed an earlier
choice, and a future session would benefit from knowing *why* without reading
the diff — it's a decisions entry. A pure bug fix with an obvious one-line
cause usually isn't; the commit message covers it.

## Format

One file per decision: `YYYY-MM-DD-short-topic.md`, structured as:

- **Problem** — what was missing or wrong, and why it mattered.
- **Decision** — what was actually built/changed.
- **Alternatives considered** — what else was on the table and why it lost,
  if anything genuinely was (skip this section if there was only one
  reasonable approach).
- **Verification** — how it was actually confirmed to work, not just that it
  compiles/passes existing tests.

Add a one-line index entry below when you add a file — newest first.

## Index

- [2026-09-26 — Private notes: the two-column layout](2026-09-26-private-notes-layout.md) — closes #138, part 3 of #132. From 840px the notes panel is a sticky column beside the form that fills the viewport's height, and Hide shrinks it to a rail. Below that it stays the #137 card. The breakpoint is 840px, not the design's 820px, because the page gutter is 24px, not 16px. The header gets its own wrapper so the narrow card stays under it.
- [2026-09-26 — Private notes: the panel](2026-09-26-private-notes-panel.md) — closes #137, part 2 of #132. A card under the anketa header, where only the author can read the notes. It uses an authenticated self-boxed key and blobs bound to anketa and author. A pure state machine drives autosave, a tab-local encrypted backup, and explicit conflict resolution ("Keep both" by default). Beyond the design: a destroyed panel makes one last save and hands its backup over to the next panel, and closing the tab warns while the user has any notes backup left, which survives a refresh. The backup key is derived from the private key, so a password change can't strand unsaved text. A conflict holds the server version until resolved. After a password reset, notes are reachable only once the counterpart re-shares.
- [2026-09-26 — Private notes: storage and API](2026-09-26-private-notes-storage-and-api.md) — closes #136, part 1 of the #132 private-notes design. A separate `anketa_private_notes` table holds each author's wrapped notes key and ciphertext, served only by its own author-scoped endpoints, with no change to shared payloads. Three places differ from the design: validation failures are 400, not 422, overwrites are one atomic conditional UPDATE, and the MySQL migration pins its collation by hand. Known limits: a save racing account deletion or the demo reset.
- [2026-09-25 — Outcome and list-entry actions keep keyboard focus](2026-09-25-outcome-and-entry-keyboard-focus.md) — closes #151. Outcomes and list entries now move focus after each action the way comments do (#149), with the helpers shared in `keepFocus.ts`. A refocus after a request is scoped to its row and dropped once the user has interacted since. A deleted row hands focus to a heading. A held Enter's auto-repeats are ignored. List-entry inputs became forms so an IME Enter never saves. A double-click's second click no longer confirms a delete.
- [2026-09-25 — Comment actions keep keyboard focus](2026-09-25-comment-thread-keyboard-focus.md) — closes #149. Every comment action used to drop keyboard focus to `<body>`, not only deleting the last comment on an emptied field (the case the issue named). `CommentThread` now moves focus explicitly after Post/Edit/Save/Cancel/Delete (Delete lands on the safe Cancel), never away from where the user moved on to. A deleted thread hands focus to its question heading. The question block was first extracted into `AnswerBlock.svelte`. The live-poll variant, where the other participant deletes the comment, is left as is. Outcomes and list entries have the same gap, tracked as #151.
- [2026-09-25 — The read-only anketa view shows only what was answered](2026-09-25-collapsed-read-only-anketa-view.md) — closes #134 and #135 (#131). In the collapsed read-only view (the counterpart's side, my own published side while not editing, both sides once archived), an unanswered field renders nothing unless it has comments, an all-empty block shows its title plus one "No answer." line, the generic "Entries"/"Details"/"Anything to add?" captions are dropped above an answer, and radio/checkbox answers show only the chosen options. It is kept separate from readonly so an in-flight Save never collapses. A few draft-loss edges on fields that get hidden are accepted and listed, plus one deferred focus edge.
- [2026-09-25 — An anketa is archived exactly once](2026-09-25-archive-exactly-once.md) — closes #130. A second archive of the same anketa used to succeed and create a second successor, forking the pair's chain. The controller now returns 409, and concurrent requests are settled by one conditional `UPDATE … WHERE archivedAt IS NULL` in the same transaction as the successor insert. The 409 carries the state that got applied. On the page, `archived` is one-way in the live-state poll, and archiving is blocked while an answers edit is open. Several related, pre-existing gaps are listed as deferred.
- [2026-09-24 — Unpublished drafts are encrypted with a key derived from the private key, not the password](2026-09-24-drafts-survive-password-change.md) — closes #129. An in-app password change no longer strands drafts, because the key they're under is no longer tied to the password. Drafts still under the old master key are read through a fallback and re-saved on open, or just before the next password change. An undecryptable draft (from before a forgotten-password reset) degrades to an empty draft with a notice, and to a flagged entry in the export, instead of breaking the page. The issue's own proposal, re-encrypting every draft to the new master key inside the password change with server-side atomicity, was built first and dropped after review.
- [2026-09-23 — The 'support_checkin' template's next cycle falls back to 'regular'](2026-09-23-support-checkin-template-does-not-recur.md) — deviates from issue #106's "repeats itself" sketch, following the career-growth precedent: self-recurrence would keep a pair on support check-ins indefinitely. Only matters when the support check-in is the pair's chain anketa, since one created next to an open regular anketa is a one-off anyway.
- [2026-09-23 — A hand-created anketa next to an open one is a one-off](2026-09-23-one-open-anketa-chain-per-pair.md) — closes #111. A new persisted `Anketa::$oneOff` flag, set at creation when the pair already has an open anketa, means no carry-forward and no auto-recreated successor. It replaced the issue's own dynamic "another open anketa" rule after review showed that rule could hand the chain to an empty ad-hoc anketa, dropping carried goals and outcomes, or end the chain on concurrent archives.
