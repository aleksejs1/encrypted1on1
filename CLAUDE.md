- **Backend** (`backend/`, hand-composed Symfony, no `symfony/skeleton`): Doctrine ORM/migrations + API Platform wired in, defaulting to plain JSON (not JSON-LD — `config/packages/api_platform.php`; kept response shapes consistent with the hand-written controllers). `User` (`isAdmin`/`isBlocked` flags) is the only API Platform resource — `GET /api/users`, read-only, unauthenticated (needed for counterpart-picking; neither flag is sensitive). `authHash`/`encryptedPrivateKey` carry no serialization group, structurally excluded from API output. Everything else is custom controllers with real logic, not generic CRUD, on a plain Symfony session (httpOnly/SameSite=Strict cookie, CSRF-protected, not JWT):
  - `ActivationController`/`AuthController`/`CsrfTokenController` (Phase 4) — `bin/console app:create-activation-link <email> [--admin]` is still the only way to *bootstrap the very first* account (Phase 6g adds a second way for everyone else: invites); `/api/me` now also returns `publicKey`/`encryptedPrivateKey` so a page refresh can re-derive the unwrapped private key (see `identity.ts` below) without a full re-login.
  - `AnketaController` (Phase 5) — `Anketa` entity: per-side `{blob, publishedAt}` pairs (one column each, draft-vs-published is opaque to the server — only `publishedAt` distinguishes them) plus `employeeSealedKey`/`managerSealedKey` (the anketa's own symmetric key, `crypto_box_seal`-ed to each participant). Every route checks the requester is a participant. Publishing is one-way this phase (no re-edit-after-publish). `meetingDate` parsing uses the lenient `new \DateTimeImmutable($string)` constructor, not `createFromFormat(DATE_ATOM, ...)` — the latter rejects the milliseconds+`Z` that JS's `toISOString()` produces.
  - Comments (Phase 6a) — one shared `commentsBlob`/`commentsVersion` pair on `Anketa`, not a row per comment (matches the spec's schema-simplicity bullet). `PUT /api/anketas/{id}/comments` takes `{blob, expectedVersion}`; a version mismatch returns 409 *with the current blob/version already in the body*, so the client can merge and retry without a second round-trip.
  - "Итоги встречи" (Phase 6b) — a second shared pair, `outcomesBlob`/`outcomesVersion` on `Anketa`, identical shape to comments (`PUT /api/anketas/{id}/outcomes`); `Anketa::saveOutcomes()` is a copy of `saveComments()`, not a shared abstraction — two instances doesn't clear that bar yet, matches `employeeBlob`/`managerBlob` also staying unabstracted.
  - "Цели" (Phase 6c) — the first plaintext, server-managed content in the app: `Goal` is a real entity/table (`id, goalUuid, anketa, author, title, description, targetDate, status`), not another blob column, per the spec's deliberate narrow exception (see below). `id` is a per-anketa snapshot row; `goalUuid` (client-generated) is what stays stable across cycles. `PUT /api/anketas/{id}/goals/{goalId}` is the first **server-enforced** ownership check in the app (`$goal->getAuthor()->getId() === $user->getId()`, else 403) — everywhere else (comments, outcome items) ownership is a client-only UI convention because the server can't see blob contents to check it; for goals it can, so it does. Progress checkpoints stay encrypted (`goalCheckpointsBlob`/`goalCheckpointsVersion`, third instance of the comments/outcomes shared-blob pattern, `PUT /api/anketas/{id}/goal-checkpoints`), with the same client-only ownership convention as outcome items. **Carry-forward** (creating a new anketa for a pair that already has an archived one) is split by the plaintext/encrypted boundary: goals carry **server-side** inside `POST /api/anketas` (a Doctrine query for the pair's most recent archived anketa, copying `in_progress` `Goal` rows with a fresh row id but the same `goalUuid`/author), while outcomes carry **client-side** (`CreateAnketa.svelte` decrypts the prior anketa's `outcomesBlob`, filters to unchecked items, re-encrypts with the new anketa's key, and passes it as an optional `outcomesBlob` field on creation — `Anketa::seedOutcomes()` sets it without touching `outcomesVersion`, which stays 0). The two "most recent anketa for pair" lookups (one Doctrine query, one client-side filter over `GET /api/anketas`) are intentionally not unified — different languages operating on different representations of the same idea. "Pair" is always the *unordered* `{employee, manager}` set — matching must ignore which one played which role last time, since roles aren't verified (see Phase 5).
  - **`src/EventListener/JsonExceptionListener.php`** (Phase 6c) — every thrown `HttpExceptionInterface` (403/404/409/401, used throughout `AnketaController` since Phase 4/5) used to render as an HTML error page, not JSON; only hand-built `JsonResponse`s were actually JSON. Found via the 6c e2e script's first real assertion on a thrown exception's body. Fixed globally (scoped to `/api/` paths), not just for the new goal endpoints — if you add a new thrown `HttpException` anywhere under `/api/`, it already gets a proper `{"error": "..."}` body for free.
  - Periodicity/auto-recreation/overdue state (Phase 6d) — `Anketa` gains `periodicityDays` (set once on a pair's first anketa, inherited by every later one) and `missed` (set only via the overdue "cancel as missed" action). **Auto-recreation is never server-side**: archiving triggers the *archiving client's own browser* to generate and seal the next anketa's key (`counterpartPublicKey` was added to `GET /api/anketas/{id}` for exactly this — public keys aren't secret, so exposing it costs nothing) and send the sealed keys as part of the `POST /api/anketas/{id}/archive` body — a server-side background job would need to generate that key itself, even if only transiently, which is precisely the kind of narrow-but-real weakening of the E2E promise this app doesn't accept without an explicit discussion. `AnketaController::createAnketaWithCarryForward()` is a small shared helper (construct `Anketa`, seed `outcomesBlob`, copy `in_progress` goals) used by both `create()` (source: a Doctrine query for the pair's most recent archived anketa) and `archive()`'s auto-recreation (source: the anketa just archived, already in hand, no query needed) — the first abstraction actually extracted across the create/archive boundary, since (unlike the 6c "most recent anketa" lookups, deliberately kept separate) this really is the same logic in the same language with two real call sites. `carryForwardOutcomes()` (`outcomes.ts`) is the client-side equivalent, called from both `CreateAnketa.svelte` and `Anketa.svelte`'s `handleArchive()`. New `PUT /api/anketas/{id}/meeting-date` powers the overdue "reschedule" action (either participant, 409 once archived). "Overdue" itself has no server-side flag — it's purely `!archivedAt && meetingDate < now`, computed client-side in both `AnketaList.svelte` and `Anketa.svelte`.
  - Reminder emails (Phase 6e) — the first thing in this app that talks to Mailer. `src/Notification/AnketaNotifier.php` builds every email body via the translator now (`TranslatorInterface::trans()`, Phase 6i — see below), still no Twig (this backend has no server-rendered views, and `trans()`'s own `%placeholder%` substitution is all the templating this needs; a reviewer can still see directly in the source that there's no code path capable of interpolating anketa content, since the notifier is never handed any). Two touchpoints: `notifyAnketaCreated()` fires synchronously from both `AnketaController::create()` and `archive()`'s auto-recreation (recipient = whoever *didn't* trigger the request); `bin/console app:send-reminders` (meant to run once daily via an **external cron entry**, not a Symfony Scheduler/Messenger worker — this compose setup has nowhere to run a persistent worker, and doesn't need one for a once-a-day batch) finds anketas whose `meetingDate` is tomorrow and sends a neutral `notifyMeetingTomorrow()` to both sides plus an extra `notifyNotFilledOut()` to whichever side hasn't published — two separate emails, not merged, matching the spec's own phrasing. `Anketa::reminderSentAt` makes the command idempotent against a same-day cron rerun. Sending is wrapped in a try/catch on `TransportExceptionInterface` (`error_log()`, no monolog-bundle in this minimal Symfony setup — not worth adding for one log line) so a mail-transport failure never fails the anketa creation/archive request it's attached to. **Known build-order trap**: `services.php`'s `bind('string $mailerFrom', ...)` broke *every* console command the moment it was added, before anything consumed it — Symfony's container won't compile with an unused named bind. Add a new bound env parameter and its first consumer in the same step, or the container is unusable in between.
  - "Отчёт за период" (Phase 6f) — the first phase to touch **no backend code at all**: the report is client-side aggregation over data already fully accessible through existing endpoints, per the spec's own reasoning ("сервер по-прежнему не видит содержимого"). No new "bulk anketas" endpoint either — bounded N+1 `GET /api/anketas/{id}` calls over an already-filtered list, deferred until 6i (group-view) actually needs the same thing at real scale. **Fixed a real cross-anketa bug found while building this**: `GoalCheckpoint.goalId` (Phase 6c) was wrongly keyed by a goal's per-anketa row `id` in `Anketa.svelte`, not its stable `goalUuid` — invisible within one anketa, but it silently broke cross-cycle checkpoint-history reconstruction, which is this report's whole point. Fixed throughout `Anketa.svelte`'s checkpoint code (goal-level comments/edits correctly stay row-`id`-scoped; only checkpoints needed the change, since only checkpoints are meant to survive carry-forward). `src/anketa/report.ts` is pure and unit-tested (no network/crypto) — `aggregateReport()` dedupes goals by `goalUuid`, keeping the latest snapshot's fields while unioning checkpoints from every occurrence. "Latest" is decided by sorting the input by each anketa's own `meetingDate` first, **not** by comparing `Goal::createdAt` — that field is only second-precision on the backend, so two snapshots created in the same second tie under a naive `>` comparison and silently keep the wrong (older) one; the real e2e script hit this directly. If you add more report-like aggregation later, sort-then-overwrite by a meaningful caller-supplied ordering beats timestamp tie-breaking every time.
  - Admin panel, invites, blocking (Phase 6g) — closes the CLI-only account-management gap from Phase 4. `User.isBlocked` is a reversible, login-only gate (`AuthController::login()` returns 403 post-credential-check, not the generic 401 — no enumeration concern, since it only fires after a *correct* password is already proven); doesn't touch data, unlike account deletion (still not built). `ActivationToken::issue()` is a static factory (moved off `CreateActivationLinkCommand`, which now calls it too) — two real call sites for the exact same token-generation logic (raw token, SHA-256 hash, `TOKEN_TTL_HOURS` expiry). `POST /api/invites` (`InviteController`) is the single mechanism behind both `REGISTRATION_MODE=invite` (any authenticated user) and `admin_only` (admin-only) — same endpoint, mode-gated internally (`$registrationMode`/`$allowedEmailDomain` bound in `services.php`, same pattern as `$mailerFrom`/`$frontendBaseUrl` — **hit the same unused-binding build-order trap 6e documented**, so `InviteController` was written in the same step as the bindings this time). Admin status is never grantable through an invite — only the CLI bootstrap or `AdminController`'s explicit `PUT /api/admin/users/{id}/admin`. `AdminController`'s routes are the first in the app gated on `$user->isAdmin()` rather than "is a participant"; includes a small, deliberately-added self-block guard (400 if you target your own account) that the spec didn't ask for but is an easy accidental-lockout footgun — no equivalent "last admin" self-demotion guard, since that's always recoverable via the CLI bootstrap and the spec doesn't call for it either. **Closes a deferred Phase 6d item**: `archive()`'s auto-recreation now checks `isBlocked()` on both participants and silently skips creating the next anketa if either is blocked, regardless of what the client requested — the "if a participant is deactivated, auto-creation stops" rule that had no state to check against until this phase added one. `REGISTRATION_MODE=domain` (open self-registration, double opt-in) and password reset are spec items **not** built this phase or scheduled on the roadmap yet — don't assume either exists.
  - Email localization (Phase 6i) — the first real use of `symfony/translation` (needs `symfony/yaml` too — the translator's YAML loader throws a clear error without it, not bundled transitively by anything else here). `translations/messages.{en,ru,lv,es}.yaml` hold the email keys (`email.anketa_created.*`, `email.meeting_tomorrow.*`, `email.not_filled_out.*`, `email.invited.*`) plus, since 6j, an `errors.*` namespace in the same files. `User.locale` (`User::SUPPORTED_LOCALES` — the backend's own copy of the same 4 codes as the frontend's `SUPPORTED_LOCALES`, kept independent since the two validate different things at different times) drives **only** which language emails to that person are sent in — `AnketaNotifier`/`InvitationNotifier` always pass `$recipient->getLocale()` as `trans()`'s explicit 4th argument, never the current request's locale or the sender's, since a reminder command has no "current request" and a notification's creator/recipient can use the app in different languages. This is deliberately **one-directional**: the frontend's displayed language (Phase 6h, `localStorage`) never reads `User.locale` back — `PUT /api/me/locale` (new, `AuthController`) is a write-only background-sync target `LanguageSwitcher.svelte` fires on every change, best-effort, not blocking the UI switch either way. `ActivationController::complete()` captures the browser's active locale at signup time (falls back to English silently on anything invalid/missing — not worth a hard validation error for a preference field) so a new account doesn't default to English emails for no reason.
  - Backend API error-message i18n (Phase 6j) — the counterpart mechanism to 6i's email localization, for a genuinely different locale source: **the requesting user's currently-active UI locale**, sent as an `X-Locale` header on every frontend API call (`client.ts`, `get(locale)` from `svelte-i18n` — imperative form since `client.ts` isn't a component), not their stored `User.locale`. `src/EventListener/RequestLocaleListener.php` resolves it into `$request`'s locale on `kernel.request` at **priority 20** — verified against the actual installed `vendor/symfony/http-kernel/EventListener/{LocaleListener,LocaleAwareListener}.php` before picking that number, not assumed: Symfony's own `LocaleListener` (priority 16) only overrides the locale via a `_locale` *routing* attribute (this app has none) or `Accept-Language` sniffing (disabled), and `LocaleAwareListener` (priority 15) is what syncs `$request->getLocale()` onto the `Translator` — so priority 20 runs safely between "after routing" and "before either of those," making the resolved locale available to a bare `$this->translator->trans('key')` in every controller with **no explicit locale argument**, unlike 6i's emails (no "current request" there, so they pass `$recipient->getLocale()` explicitly). All 5 controllers plus `CsrfGuard` now inject `TranslatorInterface` and translate every error string through the new `errors.*` YAML namespace (same 4 files as `email.*`); genuinely-repeated strings (`Not authenticated.`, the `Missing or invalid "%field%"` validation-loop message, `Anketa is archived.`, etc.) consolidate to one shared key rather than duplicating per call site. `JsonExceptionListener` needed **zero changes** — translation happens before the throw, at message-construction time, so it still just relays `$exception->getMessage()` verbatim. An invalid/missing `X-Locale` header silently falls back to English (same non-hard-error convention as 6i's activation-time locale field), not a 400.
  - **Backend test suite (Phase 7a)** — plain `phpunit/phpunit` + `symfony/browser-kit` (no `symfony/phpunit-bridge` — the app already avoids `symfony/skeleton`'s extra layers, and vanilla PHPUnit is the more standard, auditable choice). Run via `docker compose -f docker-compose.dev.yml exec backend composer test`, which wipes+re-migrates a dedicated `var/test.db` (separate from the dev DB) and clears `var/cache/test` before every run — **not optional cleanup**: `APP_DEBUG=0` in `phpunit.xml.dist` disables Symfony's container-cache freshness check entirely (a real performance trade-off Symfony makes for non-debug envs), so a stale compiled container from a previous run would otherwise silently keep serving *old* config after you edit `config/packages/test/*.php`, with no error — this exact trap was hit once while building this suite (the session-storage fix below appeared to do nothing until the cache was cleared). `backend/tests/`: `Support/ApiTestCase.php` (shared `WebTestCase` helpers — `jsonRequest()`, `activateUser()` which drives the real activation endpoint with opaque placeholder crypto strings, `secondClient()`) is used by every `Functional/*ControllerTest.php`; `Unit/Entity/*Test.php` are plain-PHP, no-kernel-boot tests for entity logic (`Anketa`'s version-guarded blob saves, `ActivationToken` expiry, `User` locale validation, `Goal::isAuthor()`). **Two real Symfony testing gotchas hit and fixed while building this, worth knowing if you touch the test setup again**: (1) `WebTestCase::createClient()` can only be called *once per test* (it's a hard `LogicException` on a second call) — multi-participant scenarios (employee + manager both logged in within one test) need `ApiTestCase::secondClient()`, which constructs a second `KernelBrowser` directly against the already-booted kernel instead; (2) the default `session.storage_factory_id` (`session.storage.factory.native`) is real PHP-native sessions, which are process-global and cannot represent two independent logged-in sessions in the same test process at all — `config/packages/test/framework.php` swaps it to `session.storage.factory.mock_file`, the fix Symfony's own docs recommend for exactly this scenario. Coverage is **breadth over exhaustiveness** by design — one test per meaningfully distinct behavior/edge case (version conflicts, ownership checks, periodicity inheritance, carry-forward, auto-recreation skip-on-blocked), not a full field-validation matrix. `InviteControllerTest` deliberately does not exercise the `admin_only` registration-mode branch — that needs a real container rebuild with a different env value (same reason Phase 6g's manual verification needed `docker compose up --force-recreate` between configs), not something one PHPUnit process can cheaply do; documented as a deferred gap in the test file itself, not silently skipped.
  - **Static analysis / architecture gates (Phase 7b)** — `phpstan/phpstan` + `phpstan/phpstan-doctrine` + `phpstan/phpstan-symfony` (via `phpstan/extension-installer`, added to `composer.json`'s `allow-plugins`), run with `docker compose exec backend composer stan`. **Split into two config files, not one**: `phpstan.neon.dist` analyses `src/` at PHPStan's max level (clean — the codebase's existing discipline, readonly properties and typed params/returns throughout, held up without a single baseline entry needed); `phpstan.tests.neon.dist` analyses `tests/` separately at level 8, one level below max — empirically confirmed before picking it (level 8: clean; level 9: 98 errors, all `offsetAccess`/`argument.type`/`encapsedStringPart` noise from `ApiTestCase::jsonRequest()`'s necessarily-`mixed` decoded-JSON return value, not real bugs — this app has no per-endpoint response DTOs anywhere, matching its own no-generic-CRUD style, so `mixed` there is the honest type, not a gap). Real `src/` fixes that came out of getting to a clean max-level baseline, worth knowing about if you touch this code: `AnketaController::archive()` now captures `$archivedAt` into a local right after calling `$anketa->archive($missed)` instead of re-reading the nullable `getArchivedAt()` afterward (PHPStan can't see across the mutator call that the field became non-null); `list()`/`findMostRecentArchivedAnketaForPair()`/`SendRemindersCommand`'s query results are annotated with `@var Anketa[]`/`@var Anketa|null` (Doctrine's `getResult()`/`getOneOrNullResult()` return bare `mixed` without them); `serializeGoal()`/`summarize()` gained precise `@return array{...}` shapes. Frontend side: no new tool (ESLint was considered and explicitly turned down — svelte-check already covers types/a11y/Svelte-specifics, the codebase already has zero `console.*`/`any`/`debugger`, and a second overlapping tool for mostly-stylistic gains didn't clear the bar) — instead `tsconfig.app.json` (the actual `src/**` config; `tsconfig.node.json` only ever covered `vite.config.ts`) gained the same `noUnusedLocals`/`noUnusedParameters`/`noFallthroughCasesInSwitch` flags `tsconfig.node.json` already had, which immediately found and removed real dead state in `Anketa.svelte`/`CreateAnketa.svelte` (`commentsVersion`/`outcomesVersion`/`goalCheckpointsVersion` local mirrors that were written but never read — every save path already re-fetches the authoritative version from the server instead of trusting a local copy — plus one genuinely-unused `GOAL_STATUS_KEYS` map, superseded by hardcoded `<option>` keys already in the template). "Architecture gates" specifically means `backend/tests/Architecture/SerializationBoundaryTest.php` (plain PHPUnit + reflection, runs via the same `composer test`, not a separate tool — Deptrac was considered and turned down: this app is 5 controllers, layering violations aren't the actual risk, and Deptrac can't express a data-exposure rule anyway) — asserts `User::$authHash`/`$encryptedPrivateKey` and every ciphertext-bearing `Anketa` property carry no `Symfony\Component\Serializer\Attribute\Groups` attribute, and that `User` is the *only* entity of the four with `#[ApiResource]`. These encode CLAUDE.md's own non-negotiable constraints as a build-breaking regression check, not just prose.
  - **CI (Phase 7c)** — `.github/workflows/ci.yml`, two independent jobs on `ubuntu-latest`, triggered on every push/PR/manual dispatch. `backend`: `shivammathur/setup-php` (PHP 8.4, `pdo_sqlite` extension — the one thing confirmed missing from the default set), then plain `composer install && composer test && composer stan` — native on the runner, not Docker, since the dev Dockerfile exists to run the FrankenPHP app server, not to execute PHPUnit/PHPStan, and both scripts are pure shell+PHP with no Docker dependency. README gained a CI badge near the top.
  - **Prod Dockerfile + prod compose (Phase 7d)** — `docker/prod/app.Dockerfile` (multi-stage: `node:22-alpine` builds the frontend, then a `dunglas/frankenphp:php8.4` stage does `composer install --no-dev` and copies the built SPA into `public/` alongside `index.php`) plus `docker/prod/Caddyfile` and `docker-compose.prod.yml` — the first way to actually run this app for real; every phase until now only ever ran `docker/dev/backend.Dockerfile` (bind-mounted source, dev Composer deps, `APP_DEBUG=1`, the `dev-placeholder-secret-not-for-production` `APP_SECRET` `backend/.env` has flagged since Phase 1). **One container serves both the SPA and the API** — FrankenPHP/Caddy already does static file serving, PHP execution, and automatic HTTPS (Let's Encrypt, triggered by setting `SERVER_NAME` to a real public domain) by itself, so a second nginx/TLS-termination container would just be extra moving parts for a self-hosted single-tenant app. The base image's *default* Caddyfile is wrong for this combined use once the SPA is added (`php_server`'s fallback sends anything without a matching Symfony route, including SPA client-side routes like `/anketas/abc-123`, into a 404 — Symfony has no route for those) — `docker/prod/Caddyfile` fixes this explicitly: `/api/*` and `/health` route to `php_server`, everything else tries the literal static file and falls back to `/index.html` so the SPA's own client-side router handles it. Confirmed via `docker inspect` that the base image's default `CMD` reads `/etc/frankenphp/Caddyfile` specifically (a second, identical-content file also happens to exist at `/etc/caddy/Caddyfile` — not the one actually used, don't COPY there by mistake). `docker-compose.prod.yml` requires every real secret via `${VAR:?message}` (`APP_SECRET`, `SERVER_NAME`, `MAILER_DSN`, `MAILER_FROM`, `FRONTEND_URL`) so it fails loudly rather than silently booting with dev placeholders; `.env.prod.example` (repo root, gitignored once copied to `.env.prod`) documents each one — deliberately a separate file from `backend/.env` (Symfony's own dev/test config, already committed) to avoid any ambiguity between the two, and deliberately *not* relying on `docker compose`'s implicit bare-`.env` auto-load. Migrations are **not** run automatically on container boot — same "documented external trigger" pattern as reminders' cron — `README.md`'s new "Production" section spells out the exact command. **Real bug caught by actually building and running the image** (not just reviewing the Dockerfile): with no `.dockerignore` at the repo root, `COPY backend/ ./` pulled in whatever gitignored local dev artifacts happened to exist in `backend/var/` on the machine doing the build — including a stray `test.db` — and since Docker seeds a fresh *named volume* from the image's existing content at the mount path on first run, that stale local data would have ended up baked into every fresh prod deployment's database. - **Non-root prod container (post-Phase-8)** — closes `private/todo.md` P4 item 16. The item's literal wording ("configurable UID/GID via env") implies the classic root-starting-entrypoint-plus-`gosu` pattern used to match a *bind-mounted* host directory's ownership — but this app's data lives in a named Docker volume, not a bind mount, so that specific motivation doesn't apply; settled with the user (`AskUserQuestion`) on a fixed non-root UID baked at build time instead, no entrypoint script, no new dependency. `docker/prod/app.Dockerfile`'s final stage now creates a fixed `app` user (UID/GID 10001, arbitrary/non-system, chosen only to avoid colliding with anything else in the base image) and ends with `USER app`. **The real technical question — can a non-root process still bind ports 80/443 — was verified for real before committing to this design, not assumed**: `setcap 'cap_net_bind_service=+ep' /usr/local/bin/frankenphp` (confirmed `libcap2-bin`, which provides `setcap`, is already installed in the base image) grants exactly that capability to the binary itself, independent of which UID runs it — proved with a real throwaway non-root+setcap image that genuinely bound port 80 and served real HTTP before this was applied to the real Dockerfile. `/app/var`, `/data` (Caddy's `XDG_DATA_HOME`), and `/config` (`XDG_CONFIG_HOME`) are `chown`'d to `app` *before* they become volume mount points — the mechanism that makes a brand-new named volume come up already owned by `app` on first run, since Docker seeds a new named volume from whatever already exists at that path in the image (the same mechanism the Phase 7d `.dockerignore` fix already relies on) — no runtime chown step needed. **Real, previously-unknown regression found and fixed in the same pass, not left for someone to discover later**: `docker/prod/restore.sh`'s `docker compose cp "$BACKUP_FILE" app:/app/var/data.db` writes the copied-in file owned by whatever UID ran the script *on the host*, not the container's own `app` user — confirmed directly (`docker cp` into a container, then `ls -l` inside it) — meaning every restore would have left the app unable to write to its own just-restored database until someone noticed and fixed permissions by hand. Fixed by adding `$COMPOSE exec -u root -T app chown app:app /app/var/data.db` right after `restore.sh`'s existing `start`; `-u root` still works even though the image's *default* user changed, since root was never removed from the image, only stopped being the default. **Verified end-to-end against real containers, at every step, not just reasoned about**: a real build of the actual `docker/prod/app.Dockerfile` confirmed `whoami`/`id` show `app`/10001 inside the running container, confirmed `/app/var`/`/data`/`/config` are all genuinely owned by `app` (not root), confirmed the app still serves real HTTP on port 80 (`/health`, a static asset, and — after running real migrations as the non-root user, proving it has genuine write access to create the SQLite schema — `/api/users`); a real `docker compose up` of the actual `docker-compose.prod.yml` (not a bare `docker run`) followed by the real, unmodified `restore.sh` script against a fake backup confirmed the exact regression above and that the fix genuinely resolves it — not just `ls -l` showing the right owner, but a real write to the restored file actually succeeding afterward. **A third real bug, this one only surfacing on the user's actual production instance after deploying this change, not caught by any of the above verification**: `chown`-ing `/app/var` in the Dockerfile only affects a *brand-new* named volume, seeded from the image on first creation — an already-existing `data:/app/var` volume from a pre-non-root deployment keeps its files' prior `root` ownership, since upgrading the image alone never touches what's already sitting in an existing volume. Symptom, reported live: `IOException: ... Permission denied` writing `var/cache/prod/translations/catalogue.ru....php` (Symfony's translation-catalogue cache, but really anything under `var/cache/prod` was equally affected) — the report page happened to be the first thing to trigger a fresh translation-cache write after the deploy. Immediate live fix plus a permanent one-time-per-existing-instance step now in `docs/deployment.md`'s "Redeploying" section: `exec -u root app chown -R app:app /app/var`, clear `var/cache/prod`, restart — the same `-u root` escape hatch `restore.sh`'s own fix above already established. Every redeploy *after* this one-time fix is unaffected, since the volume stays correctly owned by `app` from then on — this only bites the first deploy across the non-root change itself.
- **Caddy TLS certificate persistence (post-Phase-8)** — a real, previously-undiscovered bug found *while* investigating the non-root item above, confirmed and fixed in the same pass by the user's explicit choice (`AskUserQuestion`), not deferred: the base `dunglas/frankenphp:php8.4` image sets `XDG_DATA_HOME=/data`/`XDG_CONFIG_HOME=/config` (confirmed via `docker run ... env`), and Caddy's automatic-HTTPS certificate/ACME-account storage genuinely lives under `/data/caddy` (confirmed by starting real Caddy in a throwaway container and inspecting what it created there) — but neither `docker-compose.prod.yml` nor `docker-compose.prod.reverse-proxy.yml` mounted a volume at `/data`, only `data:/app/var`. Every prod redeploy recreates the container (a normal, expected part of shipping a new version — this project's own `docs/deployment.md` "Redeploying" section already tells operators to do exactly this), which wipes the container's writable layer including `/data` — so Caddy would have to re-provision a brand-new Let's Encrypt certificate from scratch on *every single redeploy*: real downtime risk, and real risk of hitting Let's Encrypt's 50-certs-per-registered-domain-per-week rate limit for anyone redeploying more than a handful of times in a week. Fixed with two new named volumes, `caddy_data:/data` and `caddy_config:/config`, added to both compose files (the reverse-proxy one gets them too, for symmetry, even though `auto_https off` there means Caddy never actually provisions certs in that mode today). **Verified the actual failure mode is fixed, not just that the YAML looks right**: since a real public domain + live ACME challenge isn't available in this sandbox, the mechanism was proven directly instead — wrote a marker file into `/data/caddy` inside a running container (standing in for what Caddy itself would persist there), removed the container entirely (the exact operation a redeploy performs), recreated it against the same named volume, and confirmed the marker file was still there, still owned by `app` — genuine proof the volume survives a container recreate, which is precisely the failure mode this closes.
- **`HEALTHCHECK` instruction + `TZ` via env (post-Phase-8)** — closes `private/todo.md` P4 items 17 and 18, done together at the user's request since both were genuinely small. **Item 17**: `docker/prod/app.Dockerfile` gained `HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 CMD curl -fsS http://127.0.0.1/health` (`curl` already present in the base image, no new package). **A real subtlety was found and designed around, not glossed over**: in direct mode (`auto_https` on), port 80 replies with a `308` redirect to HTTPS once a real domain is configured — confirmed against a real running container — and `curl -f` treats anything under 400 as success (confirmed: exit 0 on that 308), so a plain, non-redirect-following `curl -fsS` still correctly catches the failure that actually matters for a container healthcheck (FrankenPHP/Caddy crashed or hung — connection refused/timeout, confirmed separately to genuinely produce a non-zero exit) without incorrectly flapping "unhealthy" during the brief window before a fresh deployment's certificate is issued — confirmed that failure mode is real too: `-L -k` against a domain Let's Encrypt actively refuses to issue for (a fake `example.com` test domain) can't complete a TLS handshake at all, which would have made a redirect-following healthcheck permanently red on exactly the kind of transient/example-domain edge case where the app itself is otherwise fine. ## Non-negotiable constraints

- **End-to-end encryption is the entire point of this product.** The server must never be able to derive plaintext content from what it stores. When in doubt about whether something should be encrypted client-side, assume yes. The one deliberate, narrow exception is a goal's title/description/status/target date (not its progress checkpoints) — nothing else gets that exception without an explicit, discussed product decision.
- **Code must stay simple enough to audit.** This is a privacy tool; its credibility depends on a reasonably technical user being able to read the code and verify the privacy claims themselves. Prefer fewer files, fewer abstractions, and boring solutions over clever ones. Don't add speculative flexibility for requirements that don't exist yet.
- **Repository language is English, without exception** — code, comments, commit messages, docs, issue/PR templates. Working discussions with the maintainer may happen in other languages, but nothing non-English lands in this repo. (The one deliberate exception: `frontend/src/i18n/locales/{ru,lv,es}.json` and `backend/translations/messages.{ru,lv,es}.yaml` — translated *user-facing product content*, required by the spec's multilingual requirement, not repository/documentation language. Everything surrounding them — keys, code, comments — stays English.)
- **License is AGPLv3** — see [LICENSE](LICENSE). Don't introduce dependencies or vendored code under incompatible licenses without flagging it first.
