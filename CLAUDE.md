# CLAUDE.md

Guidance for Claude Code (and other AI assistants) working in this repository.

## Project

encrypted1on1 — a self-hosted, end-to-end encrypted platform for 1:1 meetings between managers and employees. See [README.md](README.md) for the overview.

## Current stage

Phases 1–5 and 6a–6e are done. "Phase 6" turned out to be a bucket (comments, "Итоги встречи"/"Цели", periodicity, reports, admin panel, i18n, typeahead/group-view) too big for one slice, same reason Phase 1 got split into seven phases — see `.claude/plans/virtual-gathering-minsky.md` for the 6a–6i breakdown and what's next (6f: "Отчёт за период").

- **Backend** (`backend/`, hand-composed Symfony, no `symfony/skeleton`): Doctrine ORM/migrations + API Platform wired in, defaulting to plain JSON (not JSON-LD — `config/packages/api_platform.php`; kept response shapes consistent with the hand-written controllers). `User` (`isAdmin` flag) is the only API Platform resource — `GET /api/users`, read-only. `authHash`/`encryptedPrivateKey` carry no serialization group, structurally excluded from API output. Everything else is custom controllers with real logic, not generic CRUD, on a plain Symfony session (httpOnly/SameSite=Strict cookie, CSRF-protected, not JWT):
  - `ActivationController`/`AuthController`/`CsrfTokenController` (Phase 4) — `bin/console app:create-activation-link <email> [--admin]` is still the only way to create an account; `/api/me` now also returns `publicKey`/`encryptedPrivateKey` so a page refresh can re-derive the unwrapped private key (see `identity.ts` below) without a full re-login.
  - `AnketaController` (Phase 5) — `Anketa` entity: per-side `{blob, publishedAt}` pairs (one column each, draft-vs-published is opaque to the server — only `publishedAt` distinguishes them) plus `employeeSealedKey`/`managerSealedKey` (the anketa's own symmetric key, `crypto_box_seal`-ed to each participant). Every route checks the requester is a participant. Publishing is one-way this phase (no re-edit-after-publish). `meetingDate` parsing uses the lenient `new \DateTimeImmutable($string)` constructor, not `createFromFormat(DATE_ATOM, ...)` — the latter rejects the milliseconds+`Z` that JS's `toISOString()` produces.
  - Comments (Phase 6a) — one shared `commentsBlob`/`commentsVersion` pair on `Anketa`, not a row per comment (matches the spec's schema-simplicity bullet). `PUT /api/anketas/{id}/comments` takes `{blob, expectedVersion}`; a version mismatch returns 409 *with the current blob/version already in the body*, so the client can merge and retry without a second round-trip.
  - "Итоги встречи" (Phase 6b) — a second shared pair, `outcomesBlob`/`outcomesVersion` on `Anketa`, identical shape to comments (`PUT /api/anketas/{id}/outcomes`); `Anketa::saveOutcomes()` is a copy of `saveComments()`, not a shared abstraction — two instances doesn't clear that bar yet, matches `employeeBlob`/`managerBlob` also staying unabstracted.
  - "Цели" (Phase 6c) — the first plaintext, server-managed content in the app: `Goal` is a real entity/table (`id, goalUuid, anketa, author, title, description, targetDate, status`), not another blob column, per the spec's deliberate narrow exception (see below). `id` is a per-anketa snapshot row; `goalUuid` (client-generated) is what stays stable across cycles. `PUT /api/anketas/{id}/goals/{goalId}` is the first **server-enforced** ownership check in the app (`$goal->getAuthor()->getId() === $user->getId()`, else 403) — everywhere else (comments, outcome items) ownership is a client-only UI convention because the server can't see blob contents to check it; for goals it can, so it does. Progress checkpoints stay encrypted (`goalCheckpointsBlob`/`goalCheckpointsVersion`, third instance of the comments/outcomes shared-blob pattern, `PUT /api/anketas/{id}/goal-checkpoints`), with the same client-only ownership convention as outcome items. **Carry-forward** (creating a new anketa for a pair that already has an archived one) is split by the plaintext/encrypted boundary: goals carry **server-side** inside `POST /api/anketas` (a Doctrine query for the pair's most recent archived anketa, copying `in_progress` `Goal` rows with a fresh row id but the same `goalUuid`/author), while outcomes carry **client-side** (`CreateAnketa.svelte` decrypts the prior anketa's `outcomesBlob`, filters to unchecked items, re-encrypts with the new anketa's key, and passes it as an optional `outcomesBlob` field on creation — `Anketa::seedOutcomes()` sets it without touching `outcomesVersion`, which stays 0). The two "most recent anketa for pair" lookups (one Doctrine query, one client-side filter over `GET /api/anketas`) are intentionally not unified — different languages operating on different representations of the same idea. "Pair" is always the *unordered* `{employee, manager}` set — matching must ignore which one played which role last time, since roles aren't verified (see Phase 5).
  - **`src/EventListener/JsonExceptionListener.php`** (Phase 6c) — every thrown `HttpExceptionInterface` (403/404/409/401, used throughout `AnketaController` since Phase 4/5) used to render as an HTML error page, not JSON; only hand-built `JsonResponse`s were actually JSON. Found via the 6c e2e script's first real assertion on a thrown exception's body. Fixed globally (scoped to `/api/` paths), not just for the new goal endpoints — if you add a new thrown `HttpException` anywhere under `/api/`, it already gets a proper `{"error": "..."}` body for free.
  - Periodicity/auto-recreation/overdue state (Phase 6d) — `Anketa` gains `periodicityDays` (set once on a pair's first anketa, inherited by every later one) and `missed` (set only via the overdue "cancel as missed" action). **Auto-recreation is never server-side**: archiving triggers the *archiving client's own browser* to generate and seal the next anketa's key (`counterpartPublicKey` was added to `GET /api/anketas/{id}` for exactly this — public keys aren't secret, so exposing it costs nothing) and send the sealed keys as part of the `POST /api/anketas/{id}/archive` body — a server-side background job would need to generate that key itself, even if only transiently, which is precisely the kind of narrow-but-real weakening of the E2E promise this app doesn't accept without an explicit discussion. `AnketaController::createAnketaWithCarryForward()` is a small shared helper (construct `Anketa`, seed `outcomesBlob`, copy `in_progress` goals) used by both `create()` (source: a Doctrine query for the pair's most recent archived anketa) and `archive()`'s auto-recreation (source: the anketa just archived, already in hand, no query needed) — the first abstraction actually extracted across the create/archive boundary, since (unlike the 6c "most recent anketa" lookups, deliberately kept separate) this really is the same logic in the same language with two real call sites. `carryForwardOutcomes()` (`outcomes.ts`) is the client-side equivalent, called from both `CreateAnketa.svelte` and `Anketa.svelte`'s `handleArchive()`. New `PUT /api/anketas/{id}/meeting-date` powers the overdue "reschedule" action (either participant, 409 once archived). "Overdue" itself has no server-side flag — it's purely `!archivedAt && meetingDate < now`, computed client-side in both `AnketaList.svelte` and `Anketa.svelte`.
  - Reminder emails (Phase 6e) — the first thing in this app that talks to Mailer. `src/Notification/AnketaNotifier.php` builds every email body as a **plain hardcoded PHP string** (no Twig — this backend has no server-rendered views and adding a templating dependency for a handful of metadata-only sentences isn't worth it; a side benefit is that a reviewer can see directly in the source that there's no code path capable of interpolating anketa content, since the notifier is never handed any). Two touchpoints: `notifyAnketaCreated()` fires synchronously from both `AnketaController::create()` and `archive()`'s auto-recreation (recipient = whoever *didn't* trigger the request); `bin/console app:send-reminders` (meant to run once daily via an **external cron entry**, not a Symfony Scheduler/Messenger worker — this compose setup has nowhere to run a persistent worker, and doesn't need one for a once-a-day batch) finds anketas whose `meetingDate` is tomorrow and sends a neutral `notifyMeetingTomorrow()` to both sides plus an extra `notifyNotFilledOut()` to whichever side hasn't published — two separate emails, not merged, matching the spec's own phrasing. `Anketa::reminderSentAt` makes the command idempotent against a same-day cron rerun. Sending is wrapped in a try/catch on `TransportExceptionInterface` (`error_log()`, no monolog-bundle in this minimal Symfony setup — not worth adding for one log line) so a mail-transport failure never fails the anketa creation/archive request it's attached to. **Known build-order trap**: `services.php`'s `bind('string $mailerFrom', ...)` broke *every* console command the moment it was added, before anything consumed it — Symfony's container won't compile with an unused named bind. Add a new bound env parameter and its first consumer in the same step, or the container is unusable in between.
- **Frontend** (`frontend/`, Svelte+Vite+TypeScript): `src/crypto/` implements the spec's crypto model end to end now — argon2id → HKDF-SHA256 split (`password.ts`), the argon2id salt deterministically derived from the normalized email (`salt.ts`, BLAKE2b — no random per-user salt, no email-enumeration side channel, no extra round-trip), X25519 keypair generation/wrapping (`keypair.ts`), anketa-key generation/sealing plus the versioned `{schemaVersion, data}` blob envelope (`anketaKey.ts`), and `sessionStorage`-based master-key handling (`session.ts`). `identity.ts` holds the current session's *unwrapped* private key in a module-level variable only (never in browser storage) — `ensureUnlocked()` re-derives it from the master-key + `/api/me` and memoizes for the tab's lifetime. All covered by Vitest unit tests (`npm run test`). Library quirks worth knowing: `libsodium-wrappers-sumo`, not the plain package (the standard build doesn't expose `crypto_pwhash`/argon2id despite having its constants); HKDF deliberately uses native WebCrypto, not libsodium (neither build exposes real HKDF extract/expand, only byte-length constants) — see `password.ts`. `src/anketa/questions.ts` is the full 7+5 question schema (four field types: radio/checkboxes/text/dated-append-list) as data, per spec; `AnswerField.svelte` renders any of them (Svelte 5 `$bindable()` needs `let`, not `const`, in the destructured `$props()` — see the plan's implementation notes if this trips you up again). `src/anketa/comments.ts` (`addComment`) and `src/anketa/outcomes.ts` (`addOutcome`/`toggleDone`) resolve concurrent writes with **reapply-on-conflict**, not a merge-by-id: fetch fresh state, apply the update function, and on a 409, re-apply that *same* update function to the state from the conflict body and retry once — never merge two independently-computed lists. See `updateComments`/`updateOutcomes` in `Anketa.svelte`. (An earlier version of this used a grow-only-set `mergeById` union instead; that's only safe for add-only conflicts — it's "remote wins for any id present in both lists," so merging a locally-computed `toggleDone` result against a conflicting remote state silently discards the toggle, since that item's id always exists on both sides. Building `toggleDone` surfaced this, so `merge.ts`/`mergeComments`/`mergeOutcomes` were removed rather than left as dead, misleading code — if you're tempted to reintroduce a merge-by-id helper for a future shared blob, re-check whether that blob only ever gets *added to*, or also edited in place.) `CommentThread.svelte` (presentational — comments in, `onSubmit(text)` out) is reused unchanged for outcome-item and goal/checkpoint comment threads, since `targetId` is just a string it doesn't care whether it points at a question field id, an outcome item id, a goal's row id, or a checkpoint id. `src/anketa/goals.ts`'s `Goal` type mirrors the plaintext API resource directly — unlike `Comment`/`OutcomeItem` there's no pure add/update function for it, since mutating a goal is just a `POST`/`PUT` call (see `handleAddGoal`/`handleSaveGoal`/`handleUpdateGoalStatus` in `Anketa.svelte`), not client-side blob math; `GoalCheckpoint`/`addCheckpoint` *do* follow the `OutcomeItem` shape, since checkpoints are still an encrypted blob record. `src/api/client.ts`'s `ApiError` carries the full parsed response `body`, not just a message string — needed to read a 409's current blob/version without a second fetch. Routing (`router.svelte.ts`, `auth.svelte.ts`) is still hand-rolled — no library — path-matched in `App.svelte`.
- `docker-compose.dev.yml` + `Makefile` (`make up`/`make down`) run the backend and Mailpit (its SMTP catcher, `mailpit:1025`, is `MAILER_DSN` in dev — see Phase 6e; view captured mail at `http://localhost:8025`); the frontend runs on the host via `npm run dev` and proxies `/health` + `/api` to the backend (see `vite.config.ts`).
- **Reminder emails need a daily cron trigger** (Phase 6e) — `bin/console app:send-reminders` isn't invoked by anything inside the app itself. Dev: run it manually inside the container (`docker compose -f docker-compose.dev.yml exec backend php bin/console app:send-reminders`) whenever you need to test it. Prod: add a real crontab entry once a prod Dockerfile/compose exists (Phase 7) — same "documented external trigger" pattern the spec already calls for on backups, not a new pattern.

## Non-negotiable constraints

- **End-to-end encryption is the entire point of this product.** The server must never be able to derive plaintext content from what it stores. When in doubt about whether something should be encrypted client-side, assume yes. The one deliberate, narrow exception is a goal's title/description/status/target date (not its progress checkpoints) — nothing else gets that exception without an explicit, discussed product decision.
- **Code must stay simple enough to audit.** This is a privacy tool; its credibility depends on a reasonably technical user being able to read the code and verify the privacy claims themselves. Prefer fewer files, fewer abstractions, and boring solutions over clever ones. Don't add speculative flexibility for requirements that don't exist yet.
- **Repository language is English, without exception** — code, comments, commit messages, docs, issue/PR templates. Working discussions with the maintainer may happen in other languages, but nothing non-English lands in this repo.
- **License is AGPLv3** — see [LICENSE](LICENSE). Don't introduce dependencies or vendored code under incompatible licenses without flagging it first.

## Working style

- This project explicitly favors dumb-and-simple over clever, and has a documented history of scope creep during planning — when a change grows noticeably beyond what was asked, say so before building it, rather than quietly expanding scope.
