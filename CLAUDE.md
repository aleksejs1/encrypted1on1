## Non-negotiable constraints

- **End-to-end encryption is the entire point of this product.** The server must never be able to derive plaintext content from what it stores. When in doubt about whether something should be encrypted client-side, assume yes. The one deliberate, narrow exception is a goal's title/description/status/target date (not its progress checkpoints) — nothing else gets that exception without an explicit, discussed product decision.
- **Code must stay simple enough to audit.** This is a privacy tool; its credibility depends on a reasonably technical user being able to read the code and verify the privacy claims themselves. Prefer fewer files, fewer abstractions, and boring solutions over clever ones. Don't add speculative flexibility for requirements that don't exist yet.
- **Repository language is English, without exception** — code, comments, commit messages, docs, issue/PR templates. Working discussions with the maintainer may happen in other languages, but nothing non-English lands in this repo. (The deliberate exceptions: `frontend/src/i18n/locales/{ru,lv,es,de,fr}.json` and `backend/translations/messages.{ru,lv,es,de,fr}.yaml` — translated *user-facing product content*, required by the spec's multilingual requirement, not repository/documentation language; and, the same reasoning, the per-locale `CONTENT` entries in `frontend/scripts/demo-fixture-content.mjs` — translated demo-account narrative text, not documentation, feeding into the same seeded demo data those UI translations describe. Everything surrounding them — keys, code, comments, the rest of that script — stays English.)
- **License is AGPLv3** — see [LICENSE](LICENSE). Don't introduce dependencies or vendored code under incompatible licenses without flagging it first.

## Working style

- This project explicitly favors dumb-and-simple over clever, and has a documented history of scope creep during planning — when a change grows noticeably beyond what was asked, say so before building it, rather than quietly expanding scope.
- Before claiming a change touching anketa keys/sealing/password-derived keys is "verified," see the `e1o1-verify-with-real-crypto` skill — it's this project's own established standard (real crypto against the real stack, not opaque placeholder strings, cleaned up afterward), not a new bar.
- **For a concurrent/async or multi-step-state change (multiple tabs, in-flight requests, session/cache invalidation), design the full state space before writing the fix, not one race at a time as review finds them.** Model the state as a single enum/union over the actual reachable states, not independent booleans that can combine into states nothing produces. Before broadening what a shared invalidation/cleanup function does, grep every existing call site and re-derive whether the new behavior is still correct for each one — not just the call site that prompted the change. The multi-tab unlock fix took 11 `code-review` rounds partly because the first pass modeled unlock state as two booleans (the same "stuck" bug then resurfaced in three different call sites, one round at a time) and broadened a shared cache-clearing function without auditing its other caller (breaking an unrelated admin-panel cache-bust two rounds later) — see `docs/decisions/2026-08-28-multi-tab-unlock-state-machine.md`.
- **Any non-trivial change (new functionality, not a one-line fix) follows this loop before being called done:** implement it, then get it reviewed by an independent agent — not self-review — via the `code-review` skill (it forks a fresh reviewer with no stake in the implementation); fix what it finds; re-review; repeat until a pass comes back with nothing but non-actionable/judgment-call notes. Then run the project's own auto-checks — the same ones CI and `pre-push` run (typecheck, format, lint/knip, unit tests, and where relevant the duplication/doc-link checks) — and confirm they're clean. Write or extend tests for whatever new functionality was added, matching the depth of the existing tests for the pattern being extended (e.g. new mutation functions get the same success/other-items-untouched/wrong-author-throws/wrong-id-throws coverage their sibling functions already have) rather than leaving it to manual verification alone.
- **Enable the git hooks once per clone** (`git config core.hooksPath .githooks`, see `README.md`'s "Git hooks" section) and don't bypass them (`--no-verify`) without a real reason — `pre-commit` autofixes formatting on staged files, `pre-push` runs a scoped typecheck plus a lockfile/manifest-sync check (`npm ci`/`composer validate`) whenever the relevant `package.json`/`composer.json` changed. That second check exists specifically because an incremental `npm install` once left `frontend/package-lock.json` out of sync in a way that passed locally but broke CI's `npm ci` outright (`docs/decisions/2026-08-22-npm-lockfile-drift-pre-push-check.md`) — after editing `package.json`/`composer.json`, verify against a genuinely clean install (`npm ci`, or a fresh `rm -rf node_modules && npm install`), not just an incremental `npm install <pkg>` on top of an already-installed tree.
